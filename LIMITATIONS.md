# Ограничения

Честный список того, что repro-packer **не умеет** или делает приблизительно.

## Зависимости

- **Версии пакетов по исходному коду не восстановить.** Они берутся только из файлов автора (`requirements*.txt`, `pyproject.toml`, `environment.yml`, `!pip install` в ноутбуке), из локальной среды (с согласия пользователя) или вводятся вручную. Остальные помечаются «версия неизвестна»; точные версии фиксирует `verify.sh` в `requirements.lock.txt` после первой успешной установки.
- **Справочник «модуль → пакет PyPI» ограничен** (~130 записей). Модуль, которого нет в справочнике, получает статус «догадка» (имя пакета = имя модуля) и требует подтверждения человеком.
- **Динамические импорты с вычисляемым именем** (`importlib.import_module(f"plugins.{name}")`) не разрешаются — только предупреждение с указанием строки.
- **Неявные зависимости** распознаются только для известного набора методов pandas (`read_excel`, `to_parquet`, `read_hdf`…) и только если в проекте есть pandas. Плагины, бэкенды и расширения (`matplotlib`-бэкенды, драйверы БД через строку подключения) не определяются.
- **Имена пакетов conda** иногда отличаются от PyPI (`pytorch` ↔ `torch`) — такие пары не сопоставляются автоматически. Пакеты из `environment.yml`, которые не импортируются в коде, в `requirements.txt` не попадают: в выгрузке `conda env export` это в основном системные библиотеки (`openssl`, `libgcc`), которых нет на PyPI. Если такой пакет нужен (бэкенд, плагин), его добавляют в таблицу вручную — отчёт перечисляет их.
- **Прямые ссылки не переносятся.** Для `pkg @ https://…` пакет попадает в `requirements.txt` без версии, строки `git+https://…`, локальные пути и path/git-зависимости Poetry пропускаются. Несколько ограничений Poetry для разных версий Python (списком) не разбираются — версия считается неизвестной.
- **`setup.py`** не разбирается (только декларативные `pyproject.toml`/`requirements.txt`/`environment.yml`).
- **Системные зависимости** (компиляторы, CUDA, GDAL, драйверы) не определяются.

## Анализ кода

- Определение версии Python — нижняя оценка по синтаксису и стандартной библиотеке плюс объявленный автором диапазон (`>=3.8,<3.11`, `^3.10`, `python=3.10` в conda). Совместимость конкретных версий пакетов с Python не проверяется.
- Пути к данным находятся по строковым литералам с «табличными» расширениями (`.csv`, `.xlsx`, `.npy`…). Файл ищется от папки скрипта, от корня проекта и по совпадающему концу пути в любой папке — так находятся `os.path.join(DATA, "x.csv")` и `Path(...) / "x.csv"`. Имена, целиком собранные из переменных или f-строк, не проверяются; ссылки `https://…` не считаются локальными файлами. Выходной файл, имя которого передано через переменную, может быть ошибочно отмечен как «не найден».
- Проверка seed — эвристика: учитываются `random.*`, `np.random.*`, `torch.*`, `tf.random.*` и генераторы `rng.*`. Seed, заданный в другом файле проекта, не виден — возможно лишнее предупреждение.
- Файлы, которые не разбираются как Python 3 (например, код на Python 2), попадают в отчёт, но их импорты не учитываются. То же для файлов с выражениями чрезвычайной вложенности (десятки тысяч слагаемых подряд).
- Ноутбуки разбираются по ячейкам. Ячейки на других языках (`%%bash`, `%%html`) пропускаются, ячейки с синтаксисом IPython (`x = !ls`, `obj?`) попадают в отчёт с номером ячейки, но их импорты не учитываются.

## Секреты

- Поиск секретов эвристический (шаблоны известных ключей и `*_password = "..."`). Это подсказка, а не аудит безопасности. Секрет в нестандартном формате может быть пропущен.

## Воспроизведение

- Побитово идентичный результат на разных ОС и оборудовании не гарантируется.
- Загруженный код не выполняется **на сервере** — это принцип. Проверку запуска выполняет человек у себя командой `verify.sh`. В автотестах это делается только для собственных демо-проектов.
- `verify.ps1` для Windows написан, но автотестами не проверяется (CI на Windows нет).
